# ADR-002: Localized Post-Event CTA Implementation

## Status

Accepted

## Date

2026-06-29

## Context

The landing page is a single Next.js App Router page composed from reusable landing components. The post-event conversion behavior is already centralized in `CTABlock`, which reads `EVENT_UTC` through `useCountdown` and switches from the pre-event checkout CTA to `WaitlistForm` after the event timestamp.

The enable-buy MVP must replace the post-event waitlist with a recording purchase path while preserving the existing sales-page structure, Kiwify checkout URL, R$ 47 offer, and guarantee messaging. The codebase has no internal checkout API, payment SDK, database, or tracking endpoint. The only existing backend surface is the dormant waitlist Server Action.

## Decision

Implement the MVP by changing the expired branch inside `CTABlock` to render a recording-focused Kiwify checkout CTA and concise post-event availability message. Use the existing `EVENT_UTC` and `KIWIFY_URL` constants. Keep checkout as a plain external link with the existing `target="_blank"` and `rel="noopener noreferrer"` attributes. Update only high-visibility CTA-adjacent copy in existing landing components when needed for post-event clarity.

## Alternatives Considered

### Alternative 1: Shared Offer Model

- **Description**: Add a typed offer-state helper or config object for pre-event and post-event copy across multiple components.
- **Pros**: Creates a single source for all offer-state copy if the page becomes a reusable live/replay campaign.
- **Cons**: Adds abstraction before the MVP proves that multiple components need dynamic offer-state logic.
- **Why rejected**: The current behavior switch already lives in `CTABlock`; the MVP can stay narrower by updating that boundary and nearby static copy.

### Alternative 2: Internal Checkout Handler

- **Description**: Route CTA clicks through an internal action or route before redirecting to Kiwify.
- **Pros**: Enables first-party click tracking and future checkout instrumentation.
- **Cons**: Adds a new API surface, redirect behavior, and failure modes without a PRD requirement for internal tracking.
- **Why rejected**: The PRD requires the existing Kiwify purchase path and does not require new analytics or payment processing.

### Alternative 3: Page-Level Offer State

- **Description**: Compute offer state in `app/page.tsx` and pass it through landing sections.
- **Pros**: Makes the whole page explicitly state-aware.
- **Cons**: Pushes client date-dependent behavior into the page composition boundary and expands prop plumbing across mostly static Server Components.
- **Why rejected**: Next.js keeps pages as Server Components by default, while `CTABlock` already owns the client-side countdown behavior.

## Consequences

### Positive

- The implementation removes the post-event purchase blocker with minimal code churn.
- The page continues to use the existing Kiwify checkout integration and constants.
- Existing waitlist code can remain as dormant coverage without driving the primary post-event UX.
- Focused tests can verify the behavior that changed without rewriting the landing page test suite.

### Negative

- Some non-CTA sections may still contain live-event language unless explicitly adjusted in the MVP copy pass.
- Offer-state copy remains localized instead of becoming a reusable model.

### Risks

- Visitors may still infer live attendance if high-visibility surrounding copy is not updated. Mitigation: update hero, price, final CTA, and FAQ copy that directly conflicts with recording access.
- "Limited time" copy may feel unsupported without a deadline. Mitigation: use restrained availability language and do not introduce a fake deadline constant.

## Implementation Notes

Update `__tests__/cta-block.test.tsx` and affected post-event Playwright expectations in `e2e/landing-page-v1.pw.ts`. Keep `WaitlistForm` and `submitWaitlistEmail` tests unless the implementation fully removes those files.
