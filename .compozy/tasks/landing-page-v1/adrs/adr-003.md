# ADR-003: Next.js Server Action for Waitlist Email Capture (Phase 1 Log-Only)

## Status

Accepted

## Date

2026-05-19

## Context

After June 28, the page must capture waitlist emails. Phase 2 will integrate an email marketing service (Mailchimp, Kit, etc.), but for Phase 1 MVP the integration is undecided. A form submission endpoint is needed that works before Phase 2 is configured.

## Decision

Implement a Next.js Server Action (`app/actions/waitlist.ts`) that receives the submitted email, validates it server-side, and logs it via `console.log` in Phase 1. The action signature and validation logic are identical to what Phase 2 will use; only the storage destination changes. `WaitlistForm` is a `"use client"` component that calls the action with `useActionState`.

## Alternatives Considered

### Alternative B: Tally / Google Forms Embed

- **Description**: Replace the waitlist section with an iframe pointing to a Tally or Google Forms URL
- **Pros**: Zero backend code; responses immediately accessible to Rafaela
- **Cons**: Breaks visual consistency; Rafaela must manage a separate third-party account; iframe CORS and mobile sizing issues add UX risk
- **Why rejected**: Visual inconsistency with the page design degrades trust; a Server Action is trivial to build and upgrades cleanly to Phase 2

### Alternative C: Server Action → Mailchimp API

- **Description**: POST directly to Mailchimp/Kit from the Server Action
- **Pros**: Emails immediately accessible to Rafaela without any Phase 2 migration
- **Cons**: Requires knowing Rafaela's email platform and API key before ship; blocks Phase 1 completion
- **Why rejected**: External dependency on an unknown service is a blocking risk for the June 21 deadline; Phase 2 migration is low-effort

## Consequences

### Positive

- Phase 1 ships without external service dependency
- Server Action validates email format before accepting submission
- Upgrading to Phase 2 requires only adding the API call inside the existing action — no component changes
- Vercel Function logs capture submitted emails for manual recovery if needed

### Negative

- Emails are not automatically delivered to Rafaela during Phase 1; someone must check Vercel logs
- Log-only storage is not durable — emails could be lost if log retention expires before Phase 2

### Risks

- Log retention window on Vercel free tier is 1 hour — mitigated by scheduling Phase 2 integration before Phase 1 goes live if possible; at minimum, document the risk for Rafaela
- Server Action requires Next.js to be deployed with server rendering enabled (not static export) — already required by App Router

## Implementation Notes

- File: `app/actions/waitlist.ts` — `"use server"` directive
- Validate with a simple regex or `z.string().email()` (Zod, if added)
- Return `{ success: boolean; error?: string }` to the client
- Phase 2: replace `console.log(email)` with the email service API call; no other changes needed
